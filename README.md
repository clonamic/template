# template

작업명세서, 개발명세서, 보고서 형식의 원본 모음이다. 형식은 여기서만 고친다. 비공개 저장소이며, 공개 플러그인에는 이 저장소를 언급하지 않고 사본만 넣는다.

## 문서

| 문서 | 하는 일 | 끝 문장 |
| --- | --- | --- |
| [작업명세서](작업명세서.md) | 사용자의 의도와 할 일을 맞춘다(요구·산출·완료·제외) | 승인 대기 — 작업명세서 |
| [개발명세서](개발명세서.md) | 무엇을 어떻게 바꾸고 어떻게 증명할지 고정한다(변경·검증·복구) | 승인 대기 — 개발명세서 |
| [보고서](보고서.md) | 결과를 증거와 함께 한 번 알린다(결과) | 없음 |

## 승인 횟수

한 작업의 승인은 많아야 두 번이다. 되도록 한 번으로 끝낸다.

| 상황 | 흐름 | 승인 |
| --- | --- | --- |
| 질문, 설명, 조회, 검토, 상태 확인 | 바로 답한다 | 0 |
| 읽기·설계만, 의도가 맞춰짐 | 바로 한다 | 0 |
| 읽기·설계만, 의도가 맞춰지지 않음 | 작업명세서 → 실행 | 1 |
| 바뀌는 것이 있음, 의도가 맞춰짐 | 개발명세서(작으면 한 줄 형식) → 실행 | 1 |
| 바뀌는 것이 있음, 의도가 맞춰지지 않음(새 작업의 첫 요청은 보통 이쪽) | 작업명세서 → 개발명세서 → 실행 | 2 |

- 의도가 맞춰졌다는 것: 사용자의 요청이나 고쳐 준 내용만으로 무엇(대상과 결과), 범위(항목과 수량, 열린 말 없음), 완료(확인 방법)가 모두 분명하다.
- 대기 중인 명세서를 사용자 의견대로 고쳐 다시 내는 것은 의도를 맞추는 일이지 승인이 아니다. 작업명세서를 고쳐 받은 뒤 의도가 맞춰졌으면 작업명세서를 다시 내지 않고 바로 개발명세서로 간다.
- 세 번째 승인은 없다. 개발명세서 승인 뒤 적힌 대상 안의 방식 변경은 묻지 않고 하고, 경계 밖이 필요하면 막힘 보고서로 멈춘다. 사용자가 요구를 바꾸면 새 작업이고 개발명세서 한 번으로 간다.
- 승인 대기 중인 명세서는 늘 하나다.

## 번호

같은 번호가 세 문서를 관통한다.

| 작업명세서 | 개발명세서 | 보고서 |
| --- | --- | --- |
| 요구1 (산출1·제외1) | 변경1 (복구1은 프로젝트 밖일 때만) | |
| 완료1 | 검증1 | 결과1 |

작업명세서 없이 바로 쓴 개발명세서는 맨 위에 요구·완료 줄을 직접 적는다. 번호가 어긋나면 `변경3 [요구1]`, `결과2 [완료2]`처럼 대응을 적는다.

## 공통 규칙

- 세 문서 모두 채팅에만 쓰고 파일로 만들지 않는다.
- 이름은 고정이다. 버전, 단계 번호, 다른 이름을 붙이지 않는다.

## 플러그인 사본

`clonamic-harness` 플러그인은 이 파일들의 바이트 단위 사본을 ASCII 이름으로 가진다.

| 원본 | 사본 (`../plugin/` 기준) |
| --- | --- |
| 작업명세서.md | clonamic-harness/skills/clonamic-spec/references/work-spec.md |
| 개발명세서.md | clonamic-harness/skills/clonamic-spec/references/dev-spec.md |
| 보고서.md | clonamic-harness/skills/clonamic-finish/references/report.md |

원본을 고친 뒤 플러그인 저장소가 옆(`../plugin`)에 있으면 사본을 맞춘다. Python 3.12 이상, 표준 라이브러리만 쓴다.

```bash
python3 scripts/sync_to_plugin.py          # 사본을 원본과 같게 덮어쓴다
python3 scripts/sync_to_plugin.py --check  # 다르면 목록을 보여 주고 1로 끝난다
```

`../plugin`이 없으면 아무것도 하지 않고 0으로 끝난다. 다른 위치는 `--plugin <경로>`로 준다.
